Задача J — бинарная min-heap с decreaseKey

Accepted · C++ · 23 июля 2026

Элементы перемещаются во время SiftUp и SiftDown, поэтому после каждого обмена необходимо обновить позиции обоих обменянных элементов.

Условие

Условие

Изначально бинарная куча пуста. Требуется самостоятельно обработать запросы:

  • insert x — вставить целое число \(x\);
  • getMin — вывести минимальный элемент; гарантируется, что куча непуста;
  • extractMin — удалить минимальный элемент, ничего не выводя; гарантируется, что куча непуста;
  • decreaseKey i delta — уменьшить на \(\Delta\) число, добавленное во время \(i\)-го запроса.

Для decreaseKey гарантируется, что:

  • запрос с номером \(i\) был запросом insert;
  • добавленное этим запросом число всё ещё находится в куче;
  • \(\Delta\ge 0\).

Важно: \(i\) — номер среди всех запросов, а не только среди запросов insert.

Ограничения:

\[ 1\le q\le 10^6,\qquad -10^9\le x\le 10^9,\qquad 0\le\Delta\le 10^9. \]

На каждый запрос getMin нужно вывести ответ в отдельной строке. Использовать готовую реализацию кучи нельзя.

Подход

Ключевое наблюдение

Обычная бинарная min-heap позволяет:

  • получить минимум из корня за \(O(1)\);
  • вставить элемент за \(O(\log n)\);
  • удалить минимум за \(O(\log n)\).

Но запрос decreaseKey i delta задаёт элемент не его текущей позицией в массиве кучи, а номером старого запроса insert.

Искать этот элемент линейным просмотром массива нельзя: один запрос стоил бы \(O(n)\), а при \(q\le 10^6\) суммарное время могло бы стать \(O(q^2)\).

Поэтому вместе с каждым значением хранится постоянный идентификатор

\[ \texttt{query\_id}, \]

а отдельный массив

\[ \texttt{position[query\_id]} \]

хранит текущий индекс этого элемента в массиве кучи.

Элементы перемещаются во время SiftUp и SiftDown, поэтому после каждого обмена необходимо обновить позиции обоих обменянных элементов.

Структура данных

Представление структуры

Элемент кучи

Каждый элемент имеет вид

\[ (\texttt{value},\texttt{query\_id}), \]

где:

  • value — текущее значение;
  • query_id — нулевой индекс запроса, которым элемент был вставлен.

Сравнение выполняется лексикографически:

  1. сначала по value;
  2. при равных значениях — по query_id.

Второй пункт не требуется для значения ответа, но задаёт строгий детерминированный порядок между равными элементами.

Массив кучи

Куча хранится в нумерованном с нуля массиве buffer_. Для вершины \(v\):

\[ \operatorname{parent}(v)=\left\lfloor\frac{v-1}{2}\right\rfloor, \qquad \operatorname{left}(v)=2v+1, \qquad \operatorname{right}(v)=2v+2. \]

Обратный индекс

Если элемент, добавленный запросом query_id, сейчас расположен в buffer_[v], то

\[ \texttt{position[query\_id]}=v. \]

Для запросов, не соответствующих живому элементу кучи, хранится \(-1\).

Входные номера запросов начинаются с единицы, а внутренние идентификаторы — с нуля. Поэтому команда

decreaseKey i delta

обращается к внутреннему идентификатору \(i-1\).

Инварианты

Инварианты

После обработки любого префикса запросов поддерживаются два связанных инварианта.

1. Инвариант кучи

Для каждой вершины \(v>0\)

\[ \texttt{buffer[parent(v)]} \preceq \texttt{buffer[v]}, \]

где \(\preceq\) — лексикографический порядок по паре \((\texttt{value},\texttt{query\_id})\).

Следовательно, корень не превосходит любой другой элемент: вдоль пути от корня к произвольной вершине значения не убывают. Поэтому buffer_[0] содержит элемент с минимальным value.

2. Инвариант позиций

Для каждого занятого индекса \(v\)

\[ \texttt{position[buffer[v].query\_id]}=v. \]

Иными словами, position_ является обратным отображением от идентификатора живого элемента к его текущей позиции в buffer_.

Эти инварианты должны сохраняться одновременно. Правильный heap order бесполезен для decreaseKey, если обратный индекс устарел; правильные позиции сами по себе не позволяют быстро находить минимум.

Базовая операция

Базовая операция SwapItems

Операция обмена:

  1. меняет местами два элемента массива;
  2. записывает новый индекс первого элемента в position_;
  3. записывает новый индекс второго элемента в position_.

Сам обмен сохраняет множество элементов. Последующие две записи восстанавливают инвариант позиций для обоих изменивших место элементов; для остальных элементов ничего не изменилось.

Поэтому все перемещения внутри SiftUp, SiftDown и ExtractMin должны выполняться только через эту операцию.

Корректность

Корректность операций

Insert(value, query_id)

Новый элемент добавляется в конец массива и его позиция сразу записывается в position_.

До вставки heap order выполнялся во всём дереве. Новый элемент является листом, поэтому возможное нарушение возникает только на ребре между ним и родителем.

SiftUp сравнивает элемент с родителем:

  • если родитель не больше элемента, инвариант уже восстановлен;
  • иначе элементы меняются местами, и возможное нарушение перемещается на один уровень вверх.

Каждый обмен уменьшает глубину текущей вершины на единицу. Поэтому процедура завершится не более чем через высоту дерева и восстановит heap order. SwapItems одновременно сохраняет корректность обратного индекса.

GetMin()

По инварианту кучи корень не превосходит ни один другой элемент. Следовательно,

\[ \texttt{buffer[0].value} \]

является минимальным текущим значением.

Проверка пустоты внутри операции не требуется благодаря гарантии условия.

ExtractMin()

Сначала запоминается корень — удаляемый минимальный элемент.

Если в куче находится один элемент, он удаляется, а его позиция становится равной \(-1\).

Иначе:

  1. корень меняется местами с последним элементом;
  2. прежний корень удаляется с конца массива;
  3. его позиция помечается как \(-1\);
  4. новый корень опускается с помощью SiftDown.

После переноса последнего элемента в корень поддеревья ниже него по-прежнему являются корректными кучами. Нарушение может находиться только между перемещённым элементом и одним из его детей.

SiftDown выбирает наименьшего среди текущей вершины и существующих детей:

  • если наименьшей остаётся текущая вершина, heap order восстановлен;
  • иначе она меняется местами с наименьшим ребёнком, и единственное возможное нарушение перемещается вниз.

Глубина увеличивается на каждом обмене, поэтому процедура завершится за \(O(\log n)\). Все обмены сохраняют инвариант позиций.

DecreaseKey(query_id, delta)

По инварианту позиций нужный элемент находится за \(O(1)\):

\[ v=\texttt{position[query\_id]}. \]

После присваивания

\[ \texttt{buffer[v].value} \mathrel{-}=\Delta \]

значение может стать меньше родителя, но не может нарушить отношения с детьми: если раньше оно не превосходило ребёнка, то после уменьшения тем более не превосходит его.

Следовательно, возможное нарушение направлено только вверх, и достаточно вызвать SiftUp(v). Использовать SiftDown после уменьшения ключа не требуется.

При \(\Delta=0\) порядок не меняется, и SiftUp сразу завершается.

Доказательство

Доказательство корректности всего алгоритма

Докажем по индукции по числу обработанных запросов, что:

  1. buffer_ содержит ровно элементы, которые были вставлены и ещё не удалены;
  2. выполняется инвариант кучи;
  3. выполняется инвариант позиций;
  4. каждый getMin выводит минимальное текущее значение.

База

До первого запроса оба массива описывают пустую кучу. Множество живых элементов пусто, а оба структурных инварианта выполнены тривиально.

Индукционный переход

  • insert добавляет ровно требуемый элемент, а SiftUp восстанавливает оба инварианта.
  • extractMin удаляет корень, который по heap order является минимальным, а SiftDown восстанавливает оба инварианта.
  • decreaseKey благодаря position_ изменяет именно элемент, вставленный указанным запросом, после чего SiftUp восстанавливает heap order и не нарушает соответствие идентификаторов позициям.
  • getMin не меняет состояние, а по инварианту кучи читает минимальный элемент из корня.

Следовательно, утверждения сохраняются после каждого запроса. Значит, алгоритм корректно выполняет все операции и печатает правильный ответ на каждый getMin.

Оценка

Сложность

Пусть \(h\) — текущий размер кучи, \(h\le q\).

Операция Время
insert \(O(\log h)\)
getMin \(O(1)\)
extractMin \(O(\log h)\)
decreaseKey \(O(\log h)\)

SiftUp и SiftDown проходят не более высоты полного бинарного дерева:

\[ \lfloor\log_2 h\rfloor. \]

Для \(q\) запросов:

\[ T(q)=O(q\log q),\qquad M(q)=O(q). \]

Память состоит из массива кучи и массива position_ длины \(q\).

Типы данных

Почему требуется int64_t

Начальное значение и отдельная поправка помещаются в 32-битный int, но один живой элемент может быть уменьшен много раз.

После последовательности операций его значение равно

\[ x-\sum_j\Delta_j. \]

При \(q\le 10^6\) и \(\Delta_j\le 10^9\) модуль накопленного изменения может иметь порядок

\[ 10^{15}, \]

что не помещается в 32-битный знаковый тип. Поэтому значение и поправка хранятся в int64_t.

Проверка

Граничные случаи

  • Куча из одного элемента: extractMin должен оставить пустой массив и установить его позицию в \(-1\).
  • Равные значения: tie-break по query_id выбирает один из минимумов детерминированно; выводимое минимальное значение не меняется.
  • \(\Delta=0\): элемент остаётся на месте либо SiftUp немедленно останавливается.
  • Уменьшение корня: у него нет родителя, поэтому SiftUp ничего не меняет.
  • Уменьшение элемента на несколько уровней: каждый обмен обязан обновлять обе записи в position_.
  • Между insert и decreaseKey могут находиться запросы других типов: идентификатором остаётся номер insert среди всех запросов.
  • GetMin и ExtractMin не проверяют пустоту, что корректно только благодаря гарантиям условия.

Failure mode

Главный failure mode

Личный тупик или первоначальная неверная идея не были указаны, поэтому они не приписываются автору.

Главная общая опасность этой реализации — обменять элементы кучи, но не обновить position_.

Рассмотрим запросы:

4
insert 5
insert 3
decreaseKey 1 4
getMin

После второй вставки 3 поднимается в корень, а 5 перемещается на индекс \(1\). Если позиции не обновились, запрос decreaseKey 1 4 ошибочно уменьшит 3, а не 5.

Правильное состояние после уменьшения:

\[ \{1,3\}, \]

поэтому ответ равен \(1\). Структура с устаревшим обратным индексом могла бы получить \(\{-1,5\}\) и вывести \(-1\).

Корневая причина: массив кучи хранит подвижные позиции, тогда как внешний запрос использует постоянный идентификатор. Между ними всегда должно поддерживаться точное обратное отображение.

Реализация

Замечания к реализации

Нумерация запросов

Цикл обрабатывает все команды с query_id от \(0\) до \(q-1\). Только операция insert сохраняет свой query_id в элементе, но команды остальных типов всё равно занимают номера.

Поэтому входное \(i\) преобразуется именно в i - 1, а отдельный счётчик вставок здесь был бы неверен.

Удалённые элементы

После ExtractMin позиция удалённого идентификатора устанавливается в \(-1\). Условие гарантирует, что будущий decreaseKey не обратится к нему, но это присваивание сохраняет полный смысл массива position_.

Заголовок для int64_t

Для стандартно переносимого кода следует явно добавить

#include <cstdint>

и использовать имя std::int64_t. Доступность неквалифицированного int64_t только через транзитивные подключения других заголовков стандартом не гарантируется.

Перенос идеи

Признаки похожих задач

Indexed heap стоит рассматривать, когда одновременно выполняются признаки:

  • требуется быстро получать или удалять экстремальный элемент;
  • последующая операция ссылается на ранее добавленный объект по его номеру, id или handle;
  • элементы меняют позиции внутри обычной бинарной кучи;
  • линейный поиск элемента перед обновлением слишком дорог;
  • изменение ключа имеет известное направление.

Направление изменения определяет просеивание:

  • уменьшение ключа в min-heap — SiftUp;
  • увеличение ключа в min-heap — SiftDown;
  • произвольная замена ключа — выбор направления после сравнения старого и нового значений.

Общий паттерн:

\[ \text{binary heap} + \text{stable object id} + \text{inverse position map}. \]

Post-Accepted

Явно отмеченные содержательные изменения

Отдельный post-Accepted пересказ не был передан, поэтому наблюдение и доказательство восстановлены из условия и предоставленного решения. Личный тупик не выдумывался.

  1. ADDITION: явно сформулированы два совместных инварианта — heap order и обратное отображение position_.
  2. CLARIFICATION: query_id — номер среди всех запросов; входной номер \(i\) преобразуется в \(i-1\).
  3. CLARIFICATION: сравнение по query_id при равных значениях нужно для детерминированного полного порядка, но не влияет на выводимое минимальное значение.

  5. PORTABILITY CORRECTION: следует явно подключить <cstdint> и использовать std::int64_t.
  6. ADDITION: failure mode с устаревшим position_ приведён как общий риск реализации, а не как заявленная автором ошибка.
