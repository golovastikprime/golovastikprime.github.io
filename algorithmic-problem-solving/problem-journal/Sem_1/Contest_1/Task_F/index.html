Задача F — число меньших элементов справа

Reviewed · C++ · 23 июля 2026

Здесь требуется более сильный результат: не одна сумма, а число инверсий, начинающихся в каждом конкретном индексе.

Условие

Условие

Дан массив

\[ a_1,a_2,\ldots,a_n, \]

где

\[ 1\le n\le 10^5, \qquad -10^9\le a_i\le10^9. \]

Для каждого индекса \(i\) требуется найти

\[ f_i= \left| \left\{ j\ \middle|\ j>i,\ a_j<a_i \right\} \right|. \]

Иными словами, \(f_i\) — количество элементов, которые одновременно:

  • находятся правее \(a_i\) в исходном массиве;
  • строго меньше \(a_i\).

Требуется вывести все \(n\) значений \(f_i\).

Пример

Пример смысла ответа

Для массива

\[ [5,2,4,2,1] \]

получаем:

\(i\) \(a_i\) меньшие элементы справа \(f_i\)
1 5 \(2,4,2,1\) 4
2 2 \(1\) 1
3 4 \(2,1\) 2
4 2 \(1\) 1
5 1 — 0

Ответ:

\[ [4,1,2,1,0]. \]

Второе число \(2\), стоящее справа от первого числа \(2\), не учитывается: неравенство в условии строгое.

Перебор

Медленное решение

Для каждого \(i\) можно просмотреть все позиции

\[ j=i+1,i+2,\ldots,n \]

и увеличить \(f_i\), если \(a_j<a_i\).

Число проверяемых пар равно

\[ \sum_{i=1}^{n}(n-i) = \frac{n(n-1)}2 = \Theta(n^2). \]

При \(n=10^5\) это порядка \(5\cdot10^9\) сравнений, поэтому полный перебор не подходит.

Подход

Ключевое наблюдение

Пара индексов

\[ (i,j),\qquad i<j,\quad a_i>a_j, \]

является инверсией. Обычный merge sort умеет подсчитывать общее число инверсий во время слияния двух отсортированных половин.

Здесь требуется более сильный результат: не одна сумма, а число инверсий, начинающихся в каждом конкретном индексе \(i\).

Для этого вместе со значением хранится его исходный индекс:

struct Item {
  int data;
  int idx;
};

Когда во время слияния найдено несколько меньших элементов справа от конкретного Item, их количество прибавляется в

f_[item.idx]

Поэтому последующая перестановка элементов при сортировке не теряет связь с позицией, для которой строится ответ.

Индексы

Почему половины merge sort соответствуют условию \(j>i\)

Вызов merge sort для исходного диапазона индексов

\[ [l,r] \]

разбивает его на

\[ [l,m] \qquad\text{и}\qquad [m+1,r]. \]

Рекурсивные вызовы только переставляют элементы внутри своей половины. Следовательно, непосредственно перед слиянием:

  • arr_1 содержит элементы, исходные индексы которых лежали в \([l,m]\);
  • arr_2 содержит элементы, исходные индексы которых лежали в \([m+1,r]\).

Поэтому для любого элемента левой половины и любого элемента правой половины автоматически выполнено условие

\[ i<j. \]

Во время слияния остаётся проверить только условие на значения:

\[ a_j<a_i. \]

Это важный факт: сортируются значения, но разделение на половины было сделано по исходному порядку индексов.

Слияние

Что означает указатель j при слиянии

Пусть обе половины уже отсортированы по значению:

\[ L=\texttt{arr\_1}, \qquad R=\texttt{arr\_2}. \]

В коде:

  • i — число уже обработанных элементов \(L\);
  • j — число уже обработанных элементов \(R\);
  • k — следующая позиция результата слияния.

Правый элемент выбирается только в случае

arr_1[i].data > arr_2[j].data

и после этого j увеличивается.

Таким образом, каждый элемент правого префикса

\[ R[0],R[1],\ldots,R[j-1] \]

был вынесен раньше некоторого ещё не обработанного элемента левой половины только потому, что оказался строго меньше него.

Так как \(L\) отсортирован, этот правый элемент также строго меньше всех следующих элементов \(L\).

Когда выбирается текущий левый элемент по условию

arr_1[i].data <= arr_2[j].data

получаем:

  1. все уже вынесенные \(j\) правых элементов строго меньше arr_1[i];
  2. первый ещё не вынесенный правый элемент не меньше arr_1[i];
  3. следовательно, среди всей правой половины ровно \(j\) элементов строго меньше текущего левого.

Поэтому обновление

f_[arr_1[i].idx] += j;

добавляет точное число новых подходящих индексов из правой половины.

Если правая половина закончилась, то все её элементы уже были вынесены и строго меньше каждого оставшегося элемента левой половины. Поэтому тот же прибавляемый счётчик j корректен и в цикле, который дописывает остаток arr_1.

Инвариант

Инвариант слияния

Перед каждой итерацией основного цикла слияния выполняются следующие утверждения.

  1. Диапазон arr[left..k) является отсортированным слиянием уже обработанных префиксов
    \[ L[0..i) \qquad\text{и}\qquad R[0..j). \]
  2. Каждый элемент обработанного правого префикса \(R[0..j)\) строго меньше каждого ещё не обработанного элемента левой половины \(L[i..n)\).
  3. Для каждого уже обработанного элемента левой половины в его ячейку f_[idx] добавлено ровно число меньших элементов из \(R\).

База

В начале

\[ i=j=0,\qquad k=l. \]

Оба обработанных префикса пусты. Записанная часть результата также пуста, а новых вкладов в f_ ещё нет. Все три утверждения выполнены.

Сохранение: выбирается правый элемент

Если

\[ R[j]<L[i], \]

правый элемент записывается в результат, после чего j увеличивается.

Поскольку \(L\) отсортирован,

\[ L[i]\le L[i+1]\le\ldots, \]

добавленный правый элемент строго меньше не только \(L[i]\), но и всех оставшихся элементов левой половины. Второй пункт инварианта сохраняется.

Ответы пока не обновляются: этот элемент будет учтён для каждого подходящего левого элемента тогда, когда тот будет вынесен в результат.

Сохранение: выбирается левый элемент

Если

\[ L[i]\le R[j], \]

все элементы \(R[0..j)\) по инварианту строго меньше \(L[i]\), а ни один элемент \(R[j..m)\) не может быть меньше \(L[i]\), поскольку \(R[j]\) — минимальный из необработанных правых элементов.

Следовательно, добавление j даёт точный вклад правой половины для этого левого элемента. После его записи первый и третий пункты инварианта сохраняются.

Завершение

Когда одна половина закончилась:

  • если закончилась левая половина, все её ответы по пересекающим половины парам уже вычислены;
  • если закончилась правая половина, для каждого оставшегося левого элемента все \(j=m\) правых элементов строго меньше него, поэтому код добавляет j при дописывании остатка.

После завершения Merge диапазон отсортирован, а все пары, пересекающие границу между половинами, учтены правильно.

Строгость

Почему равные значения не учитываются

Условие задачи требует

\[ a_j<a_i, \]

а не \(a_j\le a_i\).

При равенстве код выбирает левый элемент первым:

if (arr_1[i].data <= arr_2[j].data) {
  // берётся левый элемент
}

Правый элемент с тем же значением ещё не входит в обработанный правый префикс, поэтому не включается в j и не прибавляется к ответу.

Если заменить <= на <, то при равенстве сначала будет вынесен правый элемент. После этого он ошибочно попадёт в число «меньших».

Минимальный контрпример:

\[ [1,1]. \]

Правильный ответ равен

\[ [0,0]. \]

При неверной обработке равенства для первого элемента получилось бы \(1\).

Здесь устойчивый выбор левого элемента при равенстве нужен не ради самой сортировки, а ради точного соответствия строгому неравенству задачи.

Накопление

Почему используется +=, а не присваивание

Меньшие элементы справа от одного индекса могут находиться в разных блоках рекурсивного разбиения.

Например, часть инверсий для элемента может быть найдена в нижнем рекурсивном слиянии внутри его половины, а другая часть — позже, при слиянии этой половины с соседней.

Поэтому ответ накапливается:

f_[arr_1[i].idx] += j;

Присваивание уничтожило бы вклад, найденный на предыдущих уровнях рекурсии.

Доказательство

Доказательство корректности merge sort

Докажем по индукции по длине исходного диапазона \([l,r]\) следующее утверждение:

После MergeSort(arr, l, r) элементы диапазона отсортированы по значению, а все пары подходящих индексов, оба конца которых принадлежат этому исходному диапазону, внесли ровно один вклад в соответствующие элементы f_.

База

Если \(l\ge r\), диапазон содержит не более одного элемента.

Он уже отсортирован. Пары различных индексов внутри него отсутствуют, поэтому добавлять к ответу ничего не требуется.

Индукционный переход

Пусть утверждение верно для диапазонов меньшей длины.

Текущий диапазон разбивается на левую и правую половины. По индукционному предположению:

  • левый рекурсивный вызов сортирует левую половину и учитывает все пары, целиком лежащие в ней;
  • правый рекурсивный вызов сортирует правую половину и учитывает все пары, целиком лежащие в ней.

После этого Merge, согласно доказанному инварианту, сортирует объединённый диапазон и учитывает все подходящие пары, у которых первый индекс находится в левой половине, а второй — в правой.

Любая пара индексов внутри \([l,r]\) принадлежит ровно одному из трёх типов:

  1. оба индекса в левой половине;
  2. оба индекса в правой половине;
  3. первый индекс в левой, второй — в правой.

Эти типы попарно не пересекаются и покрывают все возможные пары \(i<j\). Следовательно, каждая подходящая пара учтена ровно один раз.

После слияния диапазон также отсортирован. Индукционный переход доказан.

Для корневого вызова диапазон содержит весь исходный массив. Поэтому после Apply():

\[ f_i= \left| \left\{ j\mid j>i,\ a_j<a_i \right\} \right| \]

для каждого исходного индекса \(i\). Это и есть требуемый ответ.

Подсчёт пар

Другой взгляд: единственный уровень подсчёта пары

Для любых двух исходных позиций \(i<j\) существует единственная наименьшая вершина рекурсии merge sort, в которой они впервые оказываются в разных половинах.

Именно при слиянии этой вершины пара рассматривается как пересекающая границу:

  • ниже этой вершины элементы принадлежат разным рекурсивным вызовам;
  • выше неё они уже находятся внутри одной и той же отсортированной половины.

Поэтому одна пара не может быть посчитана дважды. Если \(a_j<a_i\), она добавляет единицу в f_[i]; иначе не добавляет ничего.

Трассировка

Трассировка на примере

Рассмотрим

\[ [5,2,4,2,1]. \]

При корневом слиянии отсортированные половины имеют вид

\[ L=[2,4,5], \qquad R=[1,2], \]

причём каждый Item сохраняет свой исходный индекс.

  1. Сначала выносится правое значение \(1\), поэтому j = 1.
  2. Затем выносится левое значение \(2\). Ровно один правый элемент строго меньше него, поэтому к ответу исходного второго элемента прибавляется \(1\).
  3. Равное правое значение \(2\) выносится только после левого \(2\); оно не было ошибочно посчитано как меньшее.
  4. После этого j = 2, и к ответам элементов \(4\) и \(5\) добавляется по два пересекающих половины элемента.

Инверсии внутри каждой половины уже были учтены рекурсивными вызовами. После сложения вкладов всех уровней получается

\[ [4,1,2,1,0]. \]

Оценка

Сложность

Время

На каждом уровне рекурсии суммарная длина всех сливаемых диапазонов равна \(n\). Одно слияние диапазона длины \(s\) выполняется за \(\Theta(s)\), потому что каждый указатель движется только вперёд.

Число уровней равно

\[ \Theta(\log n). \]

Следовательно,

\[ T(n) = 2T(n/2)+\Theta(n) = \boxed{\Theta(n\log n)}. \]

Создание и заполнение временных векторов на каждом слиянии не меняет эту оценку: суммарно на одном уровне копируется \(\Theta(n)\) элементов.

Память

Массив f_ содержит \(n\) целых чисел. Во время одного слияния временные массивы arr_1 и arr_2 суммарно содержат длину текущего диапазона.

Когда выполняется слияние родительского диапазона, временные массивы его дочерних вызовов уже уничтожены. Поэтому пиковый, а не суммарный, размер временных массивов равен \(O(n)\).

Дополнительно стек рекурсии занимает

\[ O(\log n). \]

Итоговая дополнительная память:

\[ \boxed{\Theta(n)}. \]

Типы

Корректность выбранных типов

Максимально возможный ответ для одной позиции равен

\[ n-1\le 99999. \]

Поэтому int безопасен для:

  • каждого значения f_[i];
  • исходного индекса idx;
  • границ и указателей merge sort.

Входные значения удовлетворяют

\[ -10^9\le a_i\le10^9 \]

и также помещаются в int.

Общая сумма всех ответов могла бы достигать

\[ \frac{n(n-1)}2, \]

и для неё потребовался бы 64-битный тип. Однако программа не складывает все ответы в одну переменную, поэтому переполнения int здесь нет.

Проверка

Граничные случаи

  • \(n=1\): рекурсивный вызов сразу завершается, ответ равен \(0\).
  • Массив строго возрастает: справа нет меньших элементов, все ответы равны нулю.
  • Массив строго убывает: для нумерации с нуля ответ имеет вид
    \[ [n-1,n-2,\ldots,1,0]. \]
  • Все значения равны: благодаря условию <= ни одно равенство не считается, все ответы равны нулю.
  • Есть дубликаты в разных половинах: левый дубликат выносится раньше правого и не получает ложного вклада.
  • Отрицательные значения: алгоритм использует только обычное сравнение, знак не требует специальной обработки.
  • Минимальные и максимальные допустимые значения \(-10^9\) и \(10^9\) безопасны для int.

Реализация

Замечания к реализации

Исходный индекс обязателен

После первого же слияния позиция элемента в arr может перестать совпадать с его позицией во входе. Если обновлять ответ по текущей позиции k, результаты будут записаны не тем индексам.

Поле Item::idx сохраняет идентичность элемента независимо от перестановок.

Сортировка изменяет входной массив

Sort хранит ссылку на arr, а Apply() сортирует этот вектор на месте. Для данной программы это безопасно: после сортировки исходный порядок значений больше не используется, а ответы уже адресуются через сохранённые idx.

В переиспользуемом интерфейсе это побочное действие стоит явно указать в контракте.

Временный буфер можно переиспользовать

Текущая реализация создаёт два временных вектора в каждом вызове Merge. Это корректно и укладывается в ограничения, но вызывает много динамических выделений памяти.

Библиотечная версия merge sort обычно создаёт один буфер длины \(n\) в Apply() и переиспользует его во всех слияниях. Асимптотика останется той же:

\[ \Theta(n\log n)\text{ времени}, \qquad \Theta(n)\text{ памяти}. \]

Ссылка внутри Sort

Поле

std::vector<Item>& arr_ref_;

требует, чтобы исходный вектор жил дольше объекта Sort. В main это условие выполнено: arr создаётся раньше sr и уничтожается позже него.

Функциональных ошибок не найдено

При ограничениях из условия:

  • границы рекурсии корректны;
  • строгие сравнения обработаны правильно;
  • ответы записываются по исходным индексам;
  • переполнения используемых целых типов нет;
  • формат вывода допустим.

Переданный код вычисляет требуемые значения за \(\Theta(n\log n)\) времени и \(\Theta(n)\) дополнительной памяти.

Failure mode

Главный failure mode

Личный тупик до Accepted не был описан, поэтому он не приписывается автору. Главная логическая опасность этой модификации merge sort — доказать лишь корректность общей сортировки, но не доказать, что j является точным вкладом в ответ конкретного исходного элемента.

Нужно одновременно контролировать три факта:

  1. правая половина соответствует более поздним исходным индексам;
  2. уже вынесенный правый префикс состоит из строго меньших значений;
  3. поле idx направляет найденный вклад в правильную ячейку ответа.

Если пропустить хотя бы один из них, обычный корректный merge sort ещё не гарантирует корректность массива f_.

Вторая частая ошибка — использовать неправильное правило при равенстве. Оно меняет решаемую задачу со строгого сравнения \(a_j<a_i\) на нестрогое \(a_j\le a_i\).

Сравнение

Почему близкие подходы менее удобны

Полный перебор

Проверяет все пары и требует \(\Theta(n^2)\) времени, что слишком много при \(n=10^5\).

Сначала полностью отсортировать значения

Обычная сортировка уничтожает информацию о том, какие элементы находились справа от каждого индекса. Одного ранга значения недостаточно: условие одновременно зависит от порядка индексов и порядка значений.

Fenwick tree или segment tree

Можно идти по исходному массиву справа налево и хранить частоты уже увиденных значений после coordinate compression. Для \(a_i\) запрос префикса значений, строго меньших \(a_i\), даст требуемый ответ.

Этот подход также работает за

\[ O(n\log n) \]

времени и \(O(n)\) памяти. Он полезен как альтернативный паттерн, особенно когда кроме подсчёта появляются динамические обновления. Однако для задачи из блока сортировок модификация merge sort решает задачу непосредственно и не требует отдельной структуры данных.

Balanced BST без размеров поддеревьев

Обычное бинарное дерево поиска умеет находить и вставлять значение, но не умеет за \(O(\log n)\) возвращать количество меньших ключей. Для этого нужны частоты дубликатов и размеры поддеревьев либо специализированная order statistics tree.

Перенос идеи

Признаки похожих задач

Модификацию merge sort стоит искать, когда:

  • требуется подсчитать пары индексов \(i<j\);
  • условие на пару задаётся сравнением значений \(a_i\) и \(a_j\);
  • нужен ответ для каждого исходного индекса, а не только общая сумма;
  • пары можно разделить на лежащие внутри половин и пересекающие границу;
  • после сортировки половин пересекающие пары считаются движением двух указателей;
  • исходную идентичность элемента можно сохранить дополнительным полем idx.

Особенно важно заранее определить:

  • какое неравенство требуется — строгое или нестрогое;
  • какая половина должна выбираться при равенстве;
  • к какому концу пары относится индивидуальный ответ;
  • нужно прибавлять вклад или заменять ранее найденное значение;
  • сохраняется ли исходный индекс после перестановок.

Тот же общий приём встречается в задачах:

  • подсчёт общего числа инверсий;
  • число меньших элементов справа;
  • число больших элементов слева;
  • подсчёт пар, удовлетворяющих монотонному неравенству;
  • построение per-index статистики во время divide-and-conquer.

Post-Accepted

Явно отмеченные содержательные изменения

Отдельный post-Accepted пересказ не передавался; лог полностью восстановлен из условия на скриншоте и предоставленного решения.

  1. ADDITION: сформулировано соответствие рекурсивных половин условию \(j>i\).
  2. ADDITION: доказан инвариант слияния, объясняющий точный смысл счётчика j.
  3. ADDITION: доказано, что каждая допустимая пара учитывается ровно один раз.
  4. CLARIFICATION: поле idx нужно для адресации ответа после перестановки элементов.
  5. CLARIFICATION: += сохраняет вклады, найденные на разных уровнях рекурсии.
  6. CLARIFICATION: выбор левого элемента при равенстве реализует строгое неравенство \(a_j<a_i\).
  7. VERIFICATION: при данных ограничениях функциональных ошибок и переполнений в решении не найдено.
